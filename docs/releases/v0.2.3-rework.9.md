# v0.2.3-rework.9

This candidate fixes the GPT-6.1 Sol catalog/request discrepancy found after
`.8` deployment. It retains upstream parity `v0.2.14`, schema maximum 251,
minimum updater 1.1.6, the Rework version lineage, and manual updates.
Preparation creates no tag and publishes or deploys nothing.

## Contract fix

GPT-6.1 Sol catalogs now offer only qualified `low`, `medium`, `high`, `xhigh`,
and `max` request efforts. Unsupported upstream choices, including `ultra`,
are filtered from client copies and effective capabilities. The gateway keeps
strict request validation and does not translate `ultra` into `max`.

Filtering covers synced account metadata, OAuth and API-key manifests,
generated and pinned catalogs, public aliases, Composite account remapping,
conflicting accounts, cached observations, and final ETags. Original provider
observations, ordering, descriptions, model membership, account/group
restrictions, and legitimate GPT-5.6 Sol/Terra `ultra` behavior remain intact.
Invalid defaults select the first retained effort or remain absent when none
survive. Billing, policy ceilings/mappings, request conversion, prompt caching,
streaming, tools, and `ultrafast` service tiers keep their existing semantics.

See [acceptance regression evidence](../GPT61_ULTRA_CONTRACT_HOTFIX.md).
Synthetic fixtures reproduced the rejected advertised effort before the fix.
Independent source, protocol, and security reviews found no unresolved issues.
Exact implementation and release-preparation revisions, CI runs, and executed
qualification results are recorded in the PRs and final qualification report.

## Database and updater

No migration is required: schema 251 remains the actual maximum. This candidate
supports the existing source-schema floor 239. Upgrading an existing `.8`
installation does not require replacing updater 1.1.6. This preparation does
not install an updater or alter production settings.

## Rollback and recovery

Keep the immutable `.8` source/image and its operation-bound backup records.
This catalog-only change adds no database state, so application rollback to
`.8` remains schema-compatible at 251. Such rollback or recovery still requires
separate authorization and the established updater checks.

Updater 1.1.6 quiesces writers before backup. After possible candidate exposure,
preserve the current database and follow its `EXPOSURE_POSSIBLE` safe-state and
explicit recovery rules. Do not restore a database merely to undo a catalog
change. Historical `.7` recovery still requires its schema249 snapshot; this
candidate does not relax those controls.

No real model inference, paid provider action, production mutation, or
account-specific live availability check was performed. Production `.8`,
schema251, and updater1.1.6 remain unchanged. Reported production health comes

ongoing live health.

security checks. Local browser failures and successful exact-head CI browser
qualification are recorded separately; no failed or skipped check is presented
as a pass.
